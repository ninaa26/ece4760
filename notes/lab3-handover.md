## Measured facts (don't re-measure unless something changed)

- **IMU axes** (on this arm): `ARM_AXIS 0` (x, points toward the hinge →
  `ARM_SIGN -1`), `UP_AXIS 2` (z, up when level, `UP_SIGN +1`), `GYRO_AXIS 1`
  (y, hinge axis, `GYRO_SIGN +1`).
- **Accelerometer offsets:** x +0.07 g, z −0.22 g (subtracted in the code).
- Rest angle with motor off: about **−76 to −83 deg** (not −90: wires/stand).
- **Open-loop hold power** (duty of 6000 needed to hold each angle), from the
  stable-range run: −70: 461, −60: 1068, −50: 1819, −40: 2467, −30: 2974,
  −20: 3280, −10: 3651, 0: 3850, +10: 3530, +20: 3244, +40: 2360.
  Fits **3850 × cos(angle)^1.8** within ~100 below level. Above level it's
  noisier (+30 read 3477, +50 read 3033), probably hinge friction.
- **Motor supply limit: about 4500–5000 duty.** Open loop 4500 flings the arm
  up; 5000 can't lift it at all (arm shakes at the bottom, gyro saturates at
  ±250 deg/s). This caused every "full power but the arm won't rise" failure
  before the cap. The group's code now has `#define MOTOR_CAP 4500`.
- **The motor/supply heats up** after many full-power runs and gives less push
  for the same command (late in the session cap 4100 couldn't reach +30, which
  earlier needed ~2600). Let it cool between long sessions; re-check a known
  trial (below) at the start of a session.
- IMU read errors: **0 in every trial** once wiring was fixed.

## Why the overshoot happens (the key insight)

The power needed to hold the arm depends on the angle (table above): most at
level (3850), less above and below. With plain PID, **the I term supplies that
holding power**, built up slowly. When the target steps from 0 to +30, I still
holds the 0-deg amount (~3850) but +30 needs only ~2970, so the arm gets ~900
too much and climbs past the target until I unwinds. Evidence:

| Trial (0 → +30 → +40, Kp 100 Kd 12 Ki 80 cap 4500) | +30 overshoot | Notes |
| --- | --- | --- |
| A: no fix | 16.7 | baseline, matches the range test |
| B: target ramp 30 deg/s | **20.7 (worse)** | error lasts longer, so I builds more. Also 0 deg still at −4.8 after 6 s |
| C: I band 10 deg (I only within 10 deg) | n/a: **broken** | P alone sags >10 deg, so I never engages; arm hangs 25–35 deg low |

More Kd (16) didn't help either; less Kp (70) made it worse (overshot to 51,
aborted). So the fix has to give the right holding power directly.

## The experiment to run next: feedforward

In `tools/pid-tuning/firmware-trial/imu_demo.c`, command `f` sets `ff_gain`.
When > 0 the controller adds `ff_gain × cos(aim)^1.8` (aim = the setpoint, not
the measured angle, so it can't feed back on itself). With it, I only has to
correct small leftovers, so the overshoot should mostly disappear, and Ki can
probably come down.

**Status: compiled, committed, NOT flashed.** The Pico currently runs the
previous trial build (ramp/band/clamp, no `f`). Steps:

1. Build: in the repo, with the Pico extension's tools (see "Building" below),
   output e.g. `tools/lab3-guide/out/build/trial2/MPU6050_IMU.uf2`.
2. Flash (BOOTSEL window, below).
3. Benchmark, same as trials A–C:
   `tools/pid-tuning/trial.sh --kp 100 --kd 12 --ki 80 --cap 4500 --ff 3850 --targets=0,30,40 --secs 6 --abort 58`
4. If the overshoot drops: try lowering Ki (40, 20) and Kp, since FF now
   supplies most of the power; maybe `--ramp 60` on top.
5. Re-run the stable range with the winner, three chunks, 6 s each:
   `--targets=-70,-60,-50,-40,-30`, `--targets=-20,-10,0,10,20`,
   `--targets=0,20,30,40,50 --abort 58`. Update the table in `lab3-status.md`.
6. Then port the winning fix into the group's `week2_IMU_Demo` (or the week 3
   folder), commit, merge, push. FF is not "pure PID"; say so in the report
   (it's a standard addition, and the handout only requires PID control).

If FF doesn't help, other ideas: reset `i_term` to the FF-free difference on a
target change; clamp anti-windup (`--clamp 1`, untested on its own); ramp + FF.

## How to run a trial (you are "in the loop")

The student asked that Claude run trials one at a time, look at the result,
and choose the next one (not a fixed grid). Each call:

    tools/pid-tuning/trial.sh --kp 100 --kd 12 --ki 80 --cap 4500 --targets=0,30,40 --secs 6

It (via `pid-trial.py`): stops the motor, waits for the arm to hang still,
sends `x` cap, `r` ramp, `b` I band, `c` clamp, `f` feedforward, then
`p`/`d`/`i`, then `a` each target in turn (no stop between), records at 20 Hz,
stops the motor. Prints one line per target with: final angle (mean of last
3 s), wobble (detrended std), drift (deg/s), overshoot, rise, settle (within
3 deg), min/max angle, motor_tail (mean command, last 3 s), at_cap (fraction),
imu_errors, abort reason. Every run is appended to `/tmp/pid-trials.jsonl`.

Options: `--kp --kd --ki --cap --ramp --iband --clamp --ff --targets --secs
--abort (default 50) --manual <duty>` (open loop) `--trace <s>` (print a line
every s seconds).

Safety: the trial firmware cuts the motor itself above **+60 deg**; the script
stops it above `--abort`. Every run starts and ends with the motor off. Tell
the student before a run starts; they keep a hand on the killswitch.

**Known trial that should reproduce** (sanity check at the start of a session):
`--kp 100 --kd 12 --ki 80 --cap 4500 --secs 14` → final about 0 ± 1 deg,
overshoot ~2–3 deg, settle ~4 s. If it doesn't, check heat, power, IMU wires.

## Flashing (BOOTSEL)

There's no reset button and no openocd. Pattern that worked all day: start a
background job that waits up to 2 min for `/Volumes/RP2350`, copies the .uf2,
then checks the drive went away; **tell the student immediately** that the
window is open (unplug Pico USB, hold BOOTSEL, plug in, let go).

    for i in $(seq 1 240); do if [ -d /Volumes/RP2350 ]; then sleep 1; cp FILE.uf2 /Volumes/RP2350/ 2>/dev/null; sleep 4; [ -d /Volumes/RP2350 ] && echo "STILL IN BOOTSEL" || echo FLASHED; exit 0; fi; sleep 0.5; done; echo "Nothing was flashed"

`cp` prints "could not copy extended attributes": harmless. macOS shows
"Disk Not Ejected Properly": harmless. Afterwards, confirm the stream: open
the port, read 1.5 s, count `L,` lines and fields (trial firmware: 10 fields).
**Stale bytes from the previous firmware** can sit in the probe's buffer;
read twice before concluding which firmware is running.

The student can also flash from VS Code: open the folder on its own
(`week2_IMU_Demo`), **Compile** / **Run** in the status bar, or Terminal → Run
Task → Compile Project / Run Project. Run needs BOOTSEL first.

## Building

This Mac's host compiler can't link (Command Line Tools SDK 27), so the SDK
can't build pioasm/picotool itself. Folders whose `CMakeLists.txt` start with
the Pico VS Code extension block build fine with the extension's tools:

    export PATH=$HOME/.pico-sdk/toolchain/15_2_Rel1/bin:$HOME/.pico-sdk/cmake/v4.3.4/bin:$HOME/.pico-sdk/ninja/v1.13.2:$PATH
    export PICO_SDK_PATH=$HOME/.pico-sdk/sdk/2.3.1
    cmake -S <folder> -B <builddir> -G Ninja && cmake --build <builddir>

Folders without that block (plain course demos): add
`-DPICO_BOARD=pico2 -Dpicotool_DIR=$HOME/.pico-sdk/picotool/2.3.1/picotool`, and
for VGA projects `-Dpioasm_DIR=<repo>/tools/lab3-guide/out/pioasm-shim/pioasm`
(`tools/lab3-guide/apply.py` creates that shim). The repo's `./build.sh` uses
the older SDK in `~/Developer/pico-sdk` and won't build VGA projects here.

## Serial

- The course code's serial is **UART0 (GP0/GP1)**, not USB. Reach it through
  the Debug Probe's port.
- `screen` quits immediately in the Claude app's terminal panel. Use
  `python3 tools/pico-serial.py` (finds the port, sends CR, logs to
  `/tmp/pico-serial.log`) or the group's `week2_hover_test/serial_terminal.py`.
- **Only one program on the port at a time.** Four stale terminals once split
  the data and scrambled everything. Check with `lsof -n | grep usbmodem`
  before a trial; the trial scripts need the port to themselves.
- Week 2 command letters: `a` target + PID on, `p` `i` `d` gains, `m` manual
  duty (PID off), `s` stop, `t` plot speed. Trial firmware adds `x` `r` `b`
  `c` `f`.

## Gotchas that cost time today

- **Pico silent + VGA black after flashing** = stuck at IMU startup. The IMU
  wasn't answering (loose wire). Diagnostic firmware:
  `tools/lab3-guide/out/src/i2c_check` (prints SDA/SCL levels and WHO_AM_I
  once a second; may need rebuilding, it's in an ignored folder). The week 2
  code now frees the I2C bus at startup, but can't fix a disconnected IMU.
- **Angle reading +5 to +17 deg with the motor off** = IMU returning zeros
  (dead/disconnected): offsets turn all-zero readings into ~+17 deg.
- **Angle briefly reads impossible values (−93) in the first 0.5 s** of a
  hard start: the accelerometer sees the arm's acceleration. Harmless now.
- `argparse`: a target list starting with a minus sign must be written
  `--targets=-70,-60`.
- Don't pipe the trial script into `head`: it kills the run mid-way (the
  motor still stops, but the data is lost).
- Run trials one after another, not in a shell loop with output hidden;
  back-to-back runs once failed silently.
- The pid-sweep (automatic grid search, `tools/pid-tuning/pid-sweep.py`) needs
  the older `firmware-sweep`; it works but the in-the-loop trials were more
  useful.
