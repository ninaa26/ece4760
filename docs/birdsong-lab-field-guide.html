02What you are actually building

A Northern Cardinal whistles: an almost pure tone that slides from about 2 kHz up to 7 kHz and back, over and over. Your job is a machine that can make a pure tone at any frequency, change that frequency thousands of times per second, and let a human record and replay those frequency slides from a keypad.

The whole system is four pieces talking to each other:

  1. A timer interrupt fires at a fixed audio rate (tens of thousands of times a second). Each time it fires, the program must produce exactly one number — one audio sample.
  2. Direct Digital Synthesis (DDS) is the arithmetic that turns "I want 3417 Hz" into that stream of numbers, using nothing but addition and a lookup table.
  3. An SPI DAC (the MCP4822 chip) converts each number into a voltage. Voltage into a speaker is sound.
  4. Human input — a slide potentiometer read by the ADC, and a keypad read by scanning — decides what frequency the DDS should be producing, and when.

Everything difficult in this lab comes from one constraint: the interrupt must finish before the next one arrives. Your demo runs at Fs = 50 kHz, so you have 20 microseconds. That is why the lab makes you toggle a GPIO pin at the start and end of the interrupt and measure it on the oscilloscope — you are proving your code fits in its budget. It's also why the course uses fixed-point arithmetic instead of casually reaching for floats.

The division of labor

Inside the interrupt: only sample generation. Add to the accumulator, look up a sine value, scale it, ship it to the DAC. No printing, no waiting, no division.

Outside the interrupt, in protothreads: reading the potentiometer, scanning the keypad, deciding what note to play next. Slow, human-speed work.

03Every concept, explained plainly

Read 03.1 through 03.4 before lab if you read nothing else. The rest you can look up here while sitting at the bench.

GPIO 03.1 · foundation

A GPIO is a single pin the chip can drive high (3.3 V) or low (0 V), or read as a 1 or 0. That's all. In C you tell the SDK a pin's direction once, then set or read it:

gpio_init(15) ;
gpio_set_dir(15, GPIO_OUT) ;
gpio_put(15, 1) ;        // pin now at 3.3 V
RememberThe Pico is a 3.3 V part. Never put 5 V on a GPIO. And each pin can only supply a small current — a few milliamps — so a GPIO drives a signal, not a motor or a speaker coil.

Timers and interrupts 03.2 · foundation

An interrupt is hardware yanking the processor away from whatever it was doing to run a specific function — the ISR, interrupt service routine — and then putting it back exactly where it was. The processor doesn't ask; it's interrupted.

A timer interrupt is one triggered by a hardware counter reaching a set value. Set it to fire every 20 µs and you get a metronome that runs whether or not your main program is busy. That regularity is the whole reason audio works: a sample that arrives 3 µs late is audible distortion.

Your sample rate Fs is how often this fires. It must be at least twice the highest frequency you want to make (Nyquist). Cardinals reach 7 kHz, so anything from 20 kHz up works; your Lab1_Birdsong/birdsong.c sets #define Fs 50000 and #define DELAY 20 — a 20 µs alarm, re-armed at the top of every interrupt.

RememberAn ISR must be short, and must never wait for anything. If it takes longer than the gap between interrupts, samples get dropped and the sound falls apart.

Direct Digital Synthesis 03.3 · the core idea

You need a sine wave at an arbitrary frequency, computed forty thousand times a second, on a chip that should not be calling sin() in an interrupt. DDS solves this with a trick.

Keep a 32-bit unsigned integer called the phase accumulator. Every time the ISR fires, add a fixed number to it — the increment. When it exceeds 32 bits it silently wraps around to zero. That overflow is not a bug; it is the oscillator. One wrap = one full cycle of the wave.

So the frequency you get is just: how much you add each tick, relative to how big the counter is, times how often you tick.

// two32 = 4294967296.0  (that is 2^32)
phase_incr = (uint32_t)((desired_freq * two32) / Fs) ;

// then, once per interrupt:
phase_accum += phase_incr ;

To turn the accumulator into a wave, precompute a sine table once at startup — 256 entries covering one cycle — and use the accumulator's top 8 bits as the index. Top bits, because they change slowly and smoothly as the counter climbs; the low bits are sub-sample precision you throw away when reading the table but keep in the accumulator, which is exactly why the frequency stays accurate.

DAC_output = fix2int15(multfix15(amplitude,
                sin_table[phase_accum >> 24])) + 2048 ;

Why this is the right tool for birdsong: changing frequency means changing one integer. No phase discontinuity, no clicks, no recomputation. You can sweep 2 kHz to 7 kHz smoothly by nudging phase_incr a little on each interrupt — which is precisely what a cardinal's whistle is.

RememberAdd a constant to a counter; let it overflow; index a table with the high bits. Frequency resolution is Fs / 232 — at your 50 kHz that is about 0.0000116 Hz, far finer than you can hear.

Fixed-point arithmetic (fix15) 03.4 · the course's dialect

Floating-point numbers are convenient and, in a tight ISR, expensive and unpredictable. The course instead stores fractional numbers inside ordinary 32-bit integers: 1 sign bit, 16 integer bits, 15 fraction bits. This format is called fix15. The number 1.0 is stored as 32768.

typedef signed int fix15 ;
#define multfix15(a,b) ((fix15)((((signed long long)(a))*((signed long long)(b)))>>15))
#define float2fix15(a) ((fix15)((a)*32768.0))
#define fix2float15(a) ((float)(a)/32768.0)
#define int2fix15(a)   ((fix15)(a << 15))
#define fix2int15(a)   ((int)(a >> 15))

Addition and subtraction just work — they're integer add and subtract. Multiplication needs the shift, because multiplying two numbers that are both scaled by 32768 gives you something scaled by 32768 ², so you shift 15 bits back down. That's all multfix15 does.

RememberYour range is roughly ±65000 with a resolution of 1/32768. Overflow is silent and sounds like garbage. Use floats freely in setup code and in protothreads; use fix15 inside the ISR.

SPI and the DAC 03.5 · hardware

A DAC (digital-to-analog converter) takes a number and outputs a proportional voltage. Yours is the MCP4822: 12-bit (so values 0–4095), two independent output channels, controlled over SPI.

SPI is a four-wire protocol where your Pico is the controller and the DAC is the peripheral: a clock line (SCK), data out (MOSI, labeled SDI on the DAC), data in (MISO — unused here, the DAC never talks back), and chip select (CS), which is held low for the duration of one message. The controller generates the clock, so there's no agreed-upon baud rate to get wrong the way there is with UART.

You send the DAC one 16-bit word per sample. The top four bits are configuration, the bottom twelve are your value:

BitNameMeaning
15A/B0 = output on channel A, 1 = channel B
14BUF1 = buffered reference input
13GA1 = gain 1× (0–2.048 V), 0 = gain 2× (0–4.096 V)
12SHDN1 = channel active, 0 = shut down
11–0DATAYour 12-bit sample, 0–4095
 
#define DAC_config_chan_A 0b0011000000000000
#define DAC_config_chan_B 0b1011000000000000

DAC_data = DAC_config_chan_A | (DAC_output & 0x0fff) ;
spi_write16_blocking(SPI_PORT, &DAC_data, 1) ;

LDAC ("load DAC") is a separate pin that tells the chip to move the value you just sent into the actual output. Tie it to ground and the output updates the instant the word arrives, which is what you want.

RememberWeek 1 asks you to move the tone to the other channel. That is a one-constant change: use DAC_config_chan_B and take your signal off VOUTB instead of VOUTA.

ADC and the slide potentiometer 03.6 · hardware

An ADC is the DAC's mirror: it measures a voltage and hands you a number. The Pico's is 12-bit, so a reading of 0 means 0 V and 4095 means about 3.3 V.

A potentiometer is a resistor with a sliding tap. Wire the two outer legs to 3.3 V and ground and it becomes a voltage divider; the middle leg (the wiper) then carries a voltage that tracks the slider's position. Feed the wiper into an ADC pin and you can read the slider's position as a number.

adc_init() ;
adc_gpio_init(26) ;            // GPIO 26 is ADC channel 0
adc_select_input(0) ;

uint16_t raw = adc_read() ;                    // 0 .. 4095
float freq = (raw * 10000.0f) / 4095.0f ;      // map to 0 .. 10 kHz
RememberRead the pot in a protothread, not the ISR. Human fingers move at a few hertz; there is no reason to sample a slider forty thousand times a second.

Keypads and debouncing 03.7 · week 2

Your keypad has twelve keys but only seven wires: four rows and three columns, with a switch at each crossing. You scan it — drive one row, read which columns went active, move to the next row — and from the row/column pair you know which key is down.

The keypad demo uses #define BASE_KEYPAD_PIN 9: GPIO 9–12 are the four row outputs, GPIO 13–15 the three column inputs with internal pull-ups, and 12 keys are decoded from the pair.

The complication is bounce. A mechanical contact doesn't close cleanly; it chatters for a few milliseconds, and the processor is fast enough to see every one of those bounces as a separate press. The fix is a small state machine that only believes a change once it has seen it twice in a row, sampled maybe every 30 ms:

StateOn reading "a key is down"On reading "nothing is down"

RememberThe lab spec says "pressing/releasing the 0 key" — it wants you to act on a clean, debounced transition, once, not repeatedly while a finger rests on a key.

Protothreads 03.8 · week 2

Protothreads give you several logical tasks that look like they run at once, without a real operating system. Each thread is a function containing a loop; at points where it would otherwise wait, it yields — hands control back so other threads can run. This is cooperative multitasking: a thread that never yields starves everything else.

In this lab, the ISR handles hard real-time audio, and protothreads handle everything human: one thread scanning the keypad, one reading the pot, one printing to the serial terminal.

RememberNever use a blocking delay inside a protothread. Use the protothread yield/timer macros so other threads keep running.

Envelopes: why your tone clicks 03.9 · sounds right

Start a sine wave instantly at full volume and you get an audible click, because an abrupt jump in amplitude is a burst of energy spread across every frequency. Real birds — and real instruments — ramp up and down.

The standard fix is an amplitude envelope: multiply your sample by a value that rises over an attack period, holds through a sustain, and falls over a decay. The lab suggests a linear ramp, which is a single fix15 addition per sample. Your report needs a scope trace showing that rise, sustain and fall.

What it actually does: it controls how loud the note is over time, separately from what pitch it is. Press a key and the volume fades in over 5 ms; hold and it stays at full; release and it fades out over 5 ms.

In the code that is a multiplier called current_amplitude, from 0 to 1. Each ISR tick it steps toward full scale when the note is on and toward zero when it is off, and the sample sent to the DAC is sine × amplitude. attack_inc is 131, and 250 × 131 is about 32768 — which is 1.0 in fix15 — so it takes 250 ticks, or 5 ms, to reach full.

Two things fall out of it for freeAt zero amplitude the sine is multiplied away and the output sits at mid-scale 2048, which is silence — so muting needs no special case, and it fades rather than stopping dead. And it is the first place fixed point earns its keep in your code: multfix15 is a 64-bit integer multiply and a shift, so the interrupt still never touches a float.
RememberEnvelope shape is one of the homework questions. Linear is cheapest; a raised-cosine or exponential ramp has no slope discontinuity and clicks less, at the cost of a table lookup or a multiply. And the ISR now does a multiply it did not before — measure GPIO 2 before and after, because that difference is the code characterisation the report wants.

Spectrograms and the FFT 03.10 · how you're judged

A spectrogram is a picture of which frequencies are present over time — time on one axis, frequency on the other, brightness for loudness. The cardinal's whistle shows up as a clean line sweeping up and down.

It's computed by chopping the audio into short windows and running an FFT (Fast Fourier Transform) on each one — an algorithm that decomposes a chunk of signal into the sine waves that add up to it. Merlin does this, then pattern-matches against real recordings. Which is why matching the sweep shape matters more than perfecting the timbre: you are drawing a line on a spectrogram.

RememberYou need a spectrogram of your own output in the report. Simplest route: aux cable from the DAC into a laptop mic input, then Audacity, WaveForms, or a few lines of Python.

Two mistakes that look like a broken circuit

1 · reading milliseconds instead of microseconds

If your cursors report numbers like t1 120ms, t2 250ms, nothing is wrong with the board — the timebase is thousands of times too slow and the whole pulse train is squashed into a solid band. On a Tektronix TBS1000C the readout sits along the top of the screen; turn the Horizontal Scale knob clockwise and watch it climb:

40.0ms → 4ms → 400µs → 40µs → 4µs → 2µs

You will pass through a stretch where the trace looks like a solid block. Keep going — pulses appear once you are into microseconds, and the sample-rate readout jumps from kS/s into MS/s.

One useful thing while you are still zoomed out: the scope’s frequency readout should already say 50.0000 kHz. That is your interrupt rate, and it confirms the period is 20 µs before you have measured anything by hand.

2 · a second probe left dangling

An unconnected probe is an antenna. It picks up mains hum as a slow, wandering sine, and if the trigger source happens to be that channel your good signal will drift and refuse to lock. Press the 2 button to switch the channel off — or just unplug that probe from the scope — and set Trigger → Source → CH1.

05In lab, step by step

Written assuming you have never built a circuit on a breadboard or used an oscilloscope. Every step says what to do, why it exists, and what to do when it misbehaves. Do them in order — each one is verifiable before the next can hide a mistake inside it.

One rule that prevents most of the pain

Never wire and code at the same time. Change one thing, check that it works, then change the next. When something breaks you then know exactly which change broke it. Almost every lost hour in this lab comes from changing three things and then not knowing which one is wrong.

  1. Learn what is in front of you

    Before touching anything, know the names of the four objects on your bench.

    • The Pico 2. A small green board, about the size of a stick of gum, with metal pads down both long edges. Those pads are the pins — forty of them, numbered 1–40 going counter-clockwise from the USB connector. The GPIO numbers in the code (GPIO 5, GPIO 26) are not the same as the physical pin numbers. There is a pinout diagram printed on the lab bench and on the Pico datasheet; keep it open.
    • The breadboard. A white plastic block full of holes. Inside, the holes are secretly wired together in groups: each row of five holes on one side of the centre channel is one electrical connection. The two long strips down each edge are the power rails (marked + and −), connected the whole length. Push a wire into a hole and it is now connected to the other four holes in that row.
    • The MCP4822 DAC. A small black chip with eight legs, four per side. It straddles the centre channel of the breadboard so its two sides land in different rows.
    • Jumper wires. Stiff wires with pins on the ends. They carry a signal from one row to another.
    Why this mattersEvery wiring mistake in this lab is one of two things: a wire in the wrong strip, or a GPIO number confused with a physical pin number.

08The homework questions

The question sheet you have is from the 2021 PIC32 version of the course. The concepts transfer exactly; the numbers don't. Both are below — use the reasoning, and confirm the specific figures against the datasheet your section is actually using.

Q1 — Current per pin, and total

PIC32 (the sheet's answer): look up the "Absolute Maximum Ratings" table in the datasheet — it gives a per-pin limit and a separate total-across-all-pins limit, and the total is much less than the per-pin figure times the number of pins.

RP2040 / RP2350 equivalent: each GPIO's drive strength is configurable — 2, 4, 8 or 12 mA — and the practical ceiling on the whole board is set by the Pico's 3.3 V regulator, not by the chip. The takeaway is the same either way: a GPIO drives logic, not loads.

Q2 — What hardware do protothreads use?

Protothreads need a time base to implement its yield-until-time macros, so it claims a timer. The point of the question is that you must not reuse that timer for your own code — check the protothreads documentation for your platform to see which one is taken, then pick a different one for audio.

Q3 — Timer period at 44 kHz

With a 40 MHz clock and a prescaler of 1, the timer counts 40,000,000 times a second. For an interrupt at 44 kHz:

40,000,000 / 44,000 = 909.09 → 909 timer cycles

On the RP2040/RP2350 you express the same thing as a period in microseconds instead: 1 / 44,000 ≈ 22.7 µs between alarms. Note this whole question uses the 2021 sheet’s 44 kHz; your board runs at 50 kHz with a 20 µs alarm, so do not expect these numbers to match your code.

Q4 — DDS resolution with a 32-bit accumulator

The smallest frequency change is one unit of increment, which corresponds to:

Fs / 232 = 44,000 / 4,294,967,296 ≈ 0.0000102 Hz

Absurdly fine — which is the point. The accumulator's low bits carry fractional-sample phase, so frequency accuracy is limited by your clock, not by your arithmetic.

How a matrix keypad works

Twelve keys would need twelve wires plus a ground if every switch were wired on its own. A matrix does it with seven, by putting the switches at the crossings of four row wires and three column wires.

The columns are held high by pull-up resistors inside the Pico, so they read 1 when nothing is happening. The program drives one row low, waits a moment, reads the three columns — a column reading 0 means the switch joining that row and that column is closed. Repeat for all four rows, about thirty times a second, and you always know what is pressed.

Debouncing, concretely

A switch contact does not close cleanly. It chatters for a few milliseconds, and the Pico is fast enough to see every bounce as a separate press. Left alone, one press of 0 toggles your tone on, off, on, off. The fix is a four-state machine that refuses to believe a change until it has seen it twice.

The demo already samples at the right rate — it yields for 30,000 µs between scans, which is exactly the 30 ms sampling period this wants.

What “wrap the scan in a state machine” actually means

It sounds like you rewrite the scanning code. You don’t — you leave it completely alone.

Look at what the demo’s loop already produces. Every pass it drives the four rows, reads the columns, decodes the result, and ends up with a single number in i: which key is down, or −1 for none. Then it prints that number and yields for 30 ms.

That number is the raw reading. Reacting to every raw reading is exactly what gives you sixteen toggles from one press. The fix is to stop reacting to single readings and start watching how they change — and that is all a state machine is.

So concretely: keep the scan, delete the printf, and put your state machine where the print used to be. It runs once per pass, receives the raw reading, and decides whether anything actually happened.

You need two variables that survive between passes: the current state, and the key you are currently interested in — call it the candidate. Each pass performs exactly one transition:

Current stateReading is the candidate keyReading is −1 or a different key
NOT_PRESSEDa key appeared — remember it as the candidate, go to MAYBE_PRESSEDstay here
MAYBE_PRESSEDconfirmed — go to PRESSED and fire the press action nowit was bounce — back to NOT_PRESSED, do nothing
PRESSEDstill held — stay here and do nothinggo to MAYBE_NOT_PRESSED
MAYBE_NOT_PRESSEDit was bounce — back to PRESSED, do nothingconfirmed — go to NOT_PRESSED and fire the release action

Two things make this work. First, nothing happens on a single reading — a change has to survive two consecutive passes 30 ms apart, and contact chatter lasts only a few milliseconds, so it never survives. Second, the action fires on the transition, never while sitting in a state. PRESSED deliberately does nothing, which is why a resting finger stays silent.

Where each requirement hooks inKey 0 toggling the tone is a press action. Record mode needs both: the press starts recording, the release stops it. Compose mode in week 3 appends to a sequence on each press. All four behaviours hang off those same two transition points.

The real reason you need this

The name says “debouncing”, but the bigger job is something else. Your keypad thread wakes 33 times a second and asks is a key down? — and that stays true for as long as a finger rests there. Hold 5 for one second and you get thirty-three yeses in a row.

What you actually want to know is did a key just go down? — true exactly once, however long the finger stays. The state machine converts a condition that stays true into an event that happens once.

Bounce is the second job. The metal contacts inside a key do not close cleanly; they physically bounce, like a marble dropped on a table, going on-off-on for a few milliseconds before settling. Your eye cannot see it. A chip doing 150 million things a second sees every bounce. Sampling only every 30 ms is already slower than the bounce, so you usually miss it entirely — and requiring two agreeing readings catches the rare one that slips through.

candidate is “which key am I currently watching”. You set it when a key first appears and compare against it afterwards, so sliding a finger onto a different key does not read as the same press continuing.

The two marked spots are where your lab behaviour goes: toggling the tone when candidate is 0, arming record mode when it is 10, starting and stopping a recording for 1–9. The empty case PRESSED branch is deliberate — that gap is what stops one press firing thirty-three times.

switch — pick one branch based on a value

Read it as: look at state; whichever case matches it, run that block and skip all the others. If state is PRESSED, only that one block runs this pass; the other three are ignored entirely.

break ; means I am done, jump out of the switch. It is not optional — leave it off and C keeps running into the next case, which is a classic bug. One break at the end of every case.

You could write the same logic with if / else if / else if. switch is simply tidier when comparing one variable against several fixed values.

if and else

Exactly one of the two blocks runs, never both. The else is optional — leave it off and, when the condition is false, nothing happens and the program moves on. That turns out to matter here.

The four cases, one at a time

Three things are in play each pass: i is what the scan just found (a key 0–11, or -1 for nothing); state is where you were last pass; candidate is the key you are currently watching.

Case 1 — NOT_PRESSED: nothing was happening.
if (i != -1) asks “is the reading not −1”, meaning some key really is down. If so, candidate = i saves which key it was — you need that because next pass you must check it is still the same key — and state = MAYBE_PRESSED moves you to “I think something happened, let me check again”. There is no else: if the reading was −1 you simply stay put, which is correct.

Case 2 — MAYBE_PRESSED: confirming a press.
if (i == candidate) asks whether the key you remembered is still there. If yes, it is real: move to PRESSED, and this is the one moment you act. That line runs exactly once per press, which is the entire goal. The else catches a glitch — the key vanished or changed — and drops you back to NOT_PRESSED having done nothing.

Case 3 — PRESSED: the key is being held.
if (i != candidate) asks whether the reading has become different from your key, meaning they may have lifted; if so you move to MAYBE_NOT_PRESSED to double-check. There is deliberately no else. While the key is still down, nothing happens — you sit in PRESSED silently, pass after pass. That empty space is the whole fix: holding a key for five seconds runs this case about 165 times and produces zero extra actions.

Case 4 — MAYBE_NOT_PRESSED: confirming a release.
if (i == candidate) means the key is back and it was only a flicker, so you return to PRESSED without doing anything. The else means it is still gone, confirmed: back to NOT_PRESSED, and this is where a release fires, once. Note the mirror — case 2 confirms a press, case 4 confirms a release, same shape in opposite directions.

The shape of the whole thingEvery pass, exactly one case runs, and it does at most two things: maybe change state, and maybe fire an action. Four small blocks, no loops, no cleverness. All of the magic is in where the two action lines sit — in the transitions, not in the states. Move either one into case PRESSED and you are back to thirty-three toggles a second.

Using the debugger — and when not to

Week 2 is the first point where a debugger earns its keep. Week 1 had one interrupt and no state. Now you have a thread, a state machine, arrays filling up, and an interrupt running underneath all of it. “Print a number and squint” starts running out.

The trap: a breakpoint stops your audio

Halting at a breakpoint halts the whole processor — including the 50 kHz interrupt. The tone dies, the DAC freezes at whatever value it last received, and every timing relationship becomes meaningless while you sit there.

That is fine for logic questions and useless for timing ones. Breakpoints answer “is my state wrong?” The oscilloscope answers “is my ISR too slow?” Never swap them.

Related: never put printf inside the ISR. It is slow and blocking and will blow the 20 µs budget on its own. If you need a value out of the ISR, store it in a variable and print it from a thread.

Which thread does what — the rate decision

By now three things run at once, at three very different speeds. Getting record and playback into the right one is the structural decision of week 2, and it is easy to get wrong because it is not stated anywhere in the assignment.

The lab says to store the frequency at about 100 Hz. Your keypad thread runs at 33 Hz, because 30 ms is the debounce sampling period and you should not speed that up. So recording cannot live in the keypad thread — it would capture a third of the detail, and a fast slider gesture would come back as a staircase.

Split the job across two lanes instead:

  • The keypad thread decides the mode. * arms recording; a debounced press of 1–9 sets “now recording into key N” and resets that key’s write index; the release clears it. It sets flags and nothing more.
  • The ADC thread does the recording. It already runs at exactly 100 Hz. Each pass, if a recording is active, append the current value and advance the index. Playback is the same lane running in reverse: read the next stored value and assign it.
The mode gate you are about to need

Your ADC thread currently overwrites the phase increment on every pass, unconditionally. The moment playback starts, the potentiometer will fight the recording 100 times a second and you will hear the slider, not the bird.

Reading the pot has to be skipped while a recording is playing. That single condition is the mode gate — and it is the reason week 2 wants one named state machine for modes rather than a scattering of booleans.

1. Fix the pitch range

If phase_incr_main = (adc_val*two32)/Fs is still what you have, the pot reading is the frequency in Hz, so the slider stops at 4095 Hz. The checkpoint wants 10,000.

You have a number running 0→4095 and you want one running 0→10000, so stretch it: multiply by 10000.0/4095.0, about 2.44, before it enters the DDS formula.

Integer division will catch you

Write adc_val / 4095 * 10000 and C throws away the fraction first — you get only 0 or 10000, nothing in between. Multiply before you divide, or put a decimal point in (10000.0) to force decimal maths.

Good looks likeSlider at the top reads 10 kHz on the scope. The wave looks coarse and steppy up there — at 50,000 samples a second you only get 5 samples per cycle. Expected, not a bug.

2. Key 0 turns the sound on and off

Think of the ISR as a worker stamping out 50,000 samples a second. You want a switch on the wall saying make sound or make silence, which the worker glances at every time.

What is silence? A speaker makes noise by moving, and moving requires the voltage to change. So silence is simply: stop changing. Send the same number every time — 2048, the middle of the DAC’s 0–4095 range, which is exactly where your wave is already centred, so switching to it causes no jump.

volatile int sound_on = 1 ;     // 1 = making sound, 0 = silent

volatile tells the compiler this can change behind your back. A thread writes it, the ISR reads it. Without it the compiler may assume it never changes and cache a stale copy forever. Any variable shared between a thread and the ISR needs it.

In the ISR, wrap the line that builds DAC_data: if sound_on, do what you do now; if not, send 2048 instead of the sine value. In your press action, when candidate is 0:

sound_on = !sound_on ;

! means not — it flips 1 to 0 and 0 to 1, so each press toggles.

Good looks likePress and release 0 → silence. Again → sound. It will click on each flip; that is expected, and the envelope that fixes it is a week-3 concern.

3. Record mode

The big one — and the part people build before they understand, then have to unbuild. So: what is actually being recorded?

You are recording the slider, not the sound

Every 10 ms you write down where your hand was, converted to a pitch. That list is the recording. The audio itself is never stored anywhere — it gets rebuilt from scratch on playback, 50,000 samples a second, from those hand positions.

Think of a player piano. The paper roll does not store music; it stores which keys were pressed, and when. Feed it through a piano and the piano makes the sound again, fresh. Your array is the roll. The DDS is the piano.

One key holds one continuous sound, not a sequence of notes. Hold 3 for two seconds while sweeping the slider and you store 200 numbers — not 200 notes, but 200 samples of a single pitch sliding upward. Play it back and you hear one unbroken tone that slides exactly as your finger moved. Hold the slider still and all 200 numbers match, so you get one flat beep. The recording captures the gesture.

So key 3 might be an upward swoop, 7 a downward one, 1 a short chirp. Different keys hold different sounds; within one key it is one sound, however long you held it. Chaining them into a whole birdsong is what Compose Mode (#, week 3) is for — record the ingredients onto keys 1–9, then fire them back to back.

Why this is the whole trickReal audio would be 50,000 numbers a second; hand positions are 100 a second — five hundred times less. And playing a tape 10× faster makes everything squeaky, while playing a piano roll 10× faster plays the same notes quicker. That is why week 3’s 8–10× playback works: your hand cannot sweep at bird speed, so you record the gesture slowly and replay it fast. The pitches land exactly where you put them; only the timing compresses.
What you will notice at the benchThe interrupt never stops. It is always making sound from whatever phase_incr_main currently holds. While recording, the slider is driving it — so you hear your sweep live as you make it. While playing back, the stored list drives it instead. Same tone generator, different hand on the wheel. That swap is the mode gate, and it is the only thing that changes.

Now the mechanics. You are building nine of these lists, one per key 1–9.

Arrays are rows of numbered boxes. uint16_t recording[200] is 200 boxes numbered 0 to 199 — C starts at zero. recording[0] = 5 puts 5 in the first box. You need nine, so use a grid:

#define MAX_LEN 1000                        // 1000 / 100 Hz = 10 seconds per key
uint16_t recording[10][MAX_LEN] ;           // [which key][which slot]
int      length[10] ;                       // how many slots each key actually used

Why [10] and not [9]? So key 5’s data lives at recording[5] instead of recording[4]. Box 0 goes unused; you save a subtraction everywhere and a whole class of off-by-one bugs. length matters because a one-second hold fills 100 slots, not 1000, and playback needs to know where to stop.

Modes — what the machine is currently doing:

#define MODE_NORMAL 0    // pot controls pitch
#define MODE_ARMED  1    // pressed *, waiting to hear which key
#define MODE_RECORD 2    // capturing right now
#define MODE_PLAY   3    // replaying right now

volatile int active_key = 0 ;    // which key we are recording into or playing

Yes, the recorded pitch follows the slider. That is the whole point — you are capturing a sweep, not one steady note. Moving the slider while the key is held is how a cardinal’s 2 kHz→7 kHz whistle gets recorded in the first place.

Four different things called “frequency”

This is where the lab’s wording trips people up. Four numbers, all rates, all measured in hertz, all meaning completely different things:

WhatValueWhat it actually is
Fs, the audio sample rate50,000 HzHow often the interrupt produces one audio sample
The pitch0–10,000 HzThe number you store and hear. This is what the potentiometer sets
The recording rate100 HzHow often you take a snapshot of the pot while recording
The keypad scan rate33 HzHow often you look at the keys

So “store the frequency at ~100 Hz” means: the thing you store is a pitch — a few thousand hertz — and you store one of them a hundred times a second. The 100 Hz is not the pitch. It is how often you take its photograph.

What you are really recordingLine those stored pitches up against time and you have drawn a line on a spectrogram — rising and falling exactly as the slider moved. That line is what Merlin looks at. Recording a sweep is literally sketching the cardinal’s whistle, one snapshot every 10 ms.

The ADC thread does the actual work, because it is the one running at 100 Hz. Each pass it picks one of three jobs:

  1. Recording — read the pot, work out the pitch, set phase_incr_main as usual, and also store the frequency into recording[active_key][idx], then move the tape head forward.
  2. Playing — do not read the pot at all. Take recording[active_key][idx], turn it into an increment, put it into phase_incr_main, move the tape head forward. When idx reaches length[active_key], you are done: mode = MODE_NORMAL.
  3. Otherwise — read the pot and set the pitch. The normal theremin you already have.

idx++ means add one to idx — shorthand for idx = idx + 1.

Guard the tape head

Only store and advance while idx < MAX_LEN. Hold a key too long without this and you write past the end of the array into whatever memory happens to sit next — corrupting other variables and producing bugs that make no sense at all.

The thing that will bite you

Job 2 says do not read the pot at all. Your ADC thread currently sets phase_incr_main on every pass, unconditionally. Leave it that way and during playback the slider overwrites the recording 100 times a second — you will hear your finger, not the bird.

That is what mode is for. It is the only thing standing between you and a very confusing twenty minutes.

Week 3 in plain English

Back to the player-piano shop from section 09. The piano plays whatever note was last called out; the roll operator reads a roll and calls out notes; the manager watches the buttons and decides who does what. Week 3 gives two of them one new job each.

New job 1 — the operator turns the crank faster

Nothing about the rolls changes. The operator reads every hole, exactly as before, and simply moves through them ten times as quickly. A gesture that took you two seconds to make comes out in two tenths of a second, with every wiggle intact.

That is the whole of the speed requirement: wait 1 ms between samples instead of 10 ms.

New job 2 — the manager keeps a setlist

Until now the manager could say “play roll 3”. Now they can write down a setlist — a list of which rolls to play, in order — and then hand the whole thing to the operator at once.

The setlist is a list of numbers. It contains no sound at all. All the audio is still in the nine recordings; the setlist only says which ones, and in what order. Four key presses become a four-note phrase, and the whole thing costs four numbers.

Two layers, and only one is newKeys 1–9 hold gestures — lists of pitches, built in week 2. The setlist holds an order — a list of key numbers, added in week 3.   1. Play recordings back 8–10× faster

    The flipbook version

    You recorded 200 pictures of where the slider was — one every 10 ms. To make the flipbook play faster you have two options.

    That wait is the playback sample rate. 10,000 µs between entries is 100 per second — the rate it was recorded at — which is 1× speed. Change only the wait:

    WaitUpdates/secSpeedA 2 s recording plays in
    10,000 µs1001×2.0 s
    1,250 µs8008×0.25 s
    1,000 µs100010×0.20 s

    The array is untouched. You read every entry. You just do not dawdle.

    The number that settles it

    A two-second recording, played back as a chirp:

    ApproachPitch updates during the chirp
    Faster playback — PT_YIELD_usec(1000)200
    Skipping — sample += 825
    The technical reasonYour recording captured pitch at 100 Hz, so it can represent pitch wiggles up to about 50 Hz. Take every eighth sample and the effective rate drops to 12.5 Hz — anything faster than a slow waver is destroyed, or aliases into something that was never there. Rapid modulation is exactly what you are recording a birdsong for, which makes it the worst possible thing to throw away.

    What neither option changes

    The audio sample rate stays 50 kHz. The ISR keeps producing 50,000 samples a second no matter what the playback thread does.

    That is why this does not make chipmunks. You are speeding up how fast the pitch changes, not how fast the audio plays. The notes stay at the frequencies you recorded; the gesture just happens quicker. Piano roll, not tape.

    Doing it

    Make the interval a named constant rather than a literal, and derive it:

    #define PLAYBACK_SPEED 10      // 8 to 10, per the lab
// recording is captured at 10000 us per sample, so:
PT_YIELD_usec(10000 / PLAYBACK_SPEED) ;

    One constant, tunable by ear between 8 and 10 without hunting for a number buried in a loop. Exact anchors for the edit are below, under The five edits.

    Good looks likeRecord a two-second sweep on a key, press it, and hear a chirp lasting about 0.2 s. Same rise and fall, same pitches, a tenth of the duration.
    The one cost1 ms is a short yield. Your keypad thread wants a slot every 30 ms and the ISR fires every 20 µs, so there is plenty of room — but if playback ever sounds stuttery, that is where to look. Try 8× (1250 µs) before suspecting anything worse.

  2. Compose mode: understand it before writing it

    # starts recording a list of key numbers. Press # again and the device plays each of those keys’ recordings in turn, back to back. Four key presses become a four-note phrase.

    The thing to hold onto: compose mode stores no sound at all. It stores the numbers 3, 3, 7, 1. All the audio already lives in the nine recordings. That is why a whole birdsong costs a handful of bytes, and why re-recording key 3 changes how the phrase sounds without you touching the sequence.

    Two layers, not oneKeys 1–9 hold gestures — lists of pitches. The sequence holds an order — a list of key numbers. Week 2 built the first layer; week 3 adds the second on top. Nothing about recording or playback has to change to support it.

  4. Compose mode: the key handler

    Two additions to the press action in your debounce machine. Key # is index 11.

  5. Compose mode: chaining the playback

    The playback thread already knows how to play one recording and then set playing = false. Chaining is a small addition at exactly that point: when one recording finishes, if a sequence is running, start the next one instead of stopping.

    In words, right after the existing “playing = false”:

    1. If playing_sequence is false, you are done — behave exactly as now.
    2. Otherwise advance seq_index.
    3. If there are notes left, set record_key to sequence[seq_index] and set playing back to true. The loop starts again on the next pass with the next recording.
    4. If there are none left, playing_sequence = false. The phrase is over.
    Consider a gap between notesBack-to-back recordings run together into one continuous slur. Real birdsong has short silences between phrases, and Merlin is matching a pattern that includes them. A PT_YIELD_usec of 30–80 ms between sequence elements is one line and usually makes the result more convincing — try it both ways and keep what sounds better.
    Good looks likeThe whole phrase plays without you touching anything, and the device returns to normal tone-generator behaviour afterwards.

Which thread runs what, now there are four

Week 2 left you with three things running at once. The playback thread makes four, and week 3 adds no more — compose mode lives entirely inside the two that already exist.

Why the debounce machine belongs in the keypad thread

It sits immediately after the scan, where the printf used to be. Two reasons it cannot go anywhere else:

  • It needs the scan result. The machine’s entire input is the number the scan just produced. Put it in another thread and you would have to ship that value across a boundary for no gain at all.
  • The thread’s yield is the debounce timing. The machine works by requiring two agreeing readings, and “two readings” means two passes of this thread. Move it somewhere faster and it stops debouncing; somewhere slower and the keypad feels sluggish. The 30 ms yield is not decoration — it is the sampling period.

The division that makes week 3 cheap

keypad thread    decides WHAT should happen   // sets flags, makes no sound
playback thread  makes it happen              // writes pitches from storage
ADC thread       reads the slider             // unless something is playing
the interrupt    turns pitch into sound       // never stops, knows nothing

The keypad thread never writes phase_incr_main. The playback thread never reads a key. That separation is why compose mode needed no change to recording or playback at all — only a new flag for one thread to set and the other to notice.

It is not just the next press

The flag stays on for every press until # again. Press #, then 3, 7, 1, 1, 9 and all five land in the array. It does not clear itself — which is deliberately different from *:

Why they differIt follows from what each is collecting. A recording is one gesture and has a natural end — you let go of the key. A phrase is many notes with no natural end, so you have to say when you are finished. # is both the start and the stop.

sequence_length does two jobs

While composing it is where to write next. After composing it is how many there are — the number the playback loop compares seq_index against.

That is why sequence_length = 0 on the opening # is the whole of “start a new phrase”. You never clear the array; you just declare it empty, and the old values get overwritten as you go.

And the guardif (sequence_length < MAX_SEQUENCE) means a 33rd key press is ignored rather than written past the end of the array. Same lesson as the recording index: anything you write into needs a bound.

Why the new variables sit at file scope

They go just below int record_key = -1;, outside every function, for two reasons.

  • Both threads need them. The keypad thread writes sequence[] when you press digits; the playback thread reads it to choose the next note. A variable declared inside one function is invisible to the other.

Where the phrase actually plays from

Once the numbers are in sequence[], two separate pieces of code turn them into sound — and neither one plays the whole phrase. They hand off to each other.

Place 1 — the # handler, in the keypad thread. This fires the first note only:

    record_key = sequence[0] ;     // that slot's key number
    playing_sequence = true ;      // "a phrase is running"
    playing = true ;               // wake the playback thread
    tone = true ;
}

Then it is finished. The keypad thread goes back to scanning keys and never touches notes two, three or four.

Place 2 — the playback thread, immediately after playing = false;, at the moment a recording ends. This fires every note after the first:

playing = false;

if (playing_sequence) {
    do {
        seq_index++ ;
    } while (seq_index < sequence_length &&
             record_length[sequence[seq_index]] == 0) ;

    if (seq_index < sequence_length) {
        record_key = sequence[seq_index] ;
        PT_YIELD_usec(NOTE_GAP_US) ;
        playing = true ;           // go round again
    } else {
        playing_sequence = false ; // phrase over
    }
}
Why it has to be splitThe playback thread can only play one recording at a time — its for loop walks a single key’s samples and then exits. So a phrase is built by re-entering that loop. Setting playing = true at the bottom means the enclosing while(1) comes back around, sees the flag, and starts the next recording. Four notes is four trips through the same loop.
What playing_sequence is forIt is the flag that says keep going. Without it, playing = false would simply stop after note one — which is exactly what your week 2 code did, because there was no phrase to continue.

Lookup Table. Values computed once at boot so the ISR only has to index an array. Your 256-entry sine table.
fix15
The course’s fixed-point format: a 32-bit int with 15 fractional bits. 1.0 is stored as 32768.
MSB / LSB
Most / Least Significant Bit. The DDS uses the accumulator’s top 8 bits and discards the rest when indexing.
Nyquist
You can only represent frequencies below half your sample rate.
Aliasing
What happens when you break that rule: a too-high frequency comes out sounding like a different, lower one.
FFT
Fast Fourier Transform. Decomposes a chunk of signal into the sine waves that make it up.
Spectrogram
Frequency versus time picture of a sound. What Merlin matches against.
Envelope
How loudness changes over a note: attack, sustain, decay.
ADSR
Attack, Decay, Sustain, Release — the standard four-stage envelope shape.

At the bench

Breadboard
Plastic block whose holes are pre-wired in strips of five, so you can join components without soldering.
Rail
The long strips down a breadboard’s edges, carrying power and ground the full length.
VDD / VSS
Power and ground pins on a chip. VDD is the positive supply; VSS is ground.
Pull-up
A resistor that holds a pin high when nothing else is driving it. The Pico has them built in, used for the keypad columns.
Voltage divider
Two resistances in series; the point between them sits at a fraction of the supply. What a potentiometer is.
Pot
Potentiometer. A resistor with a sliding tap.
Wiper
The moving contact in a potentiometer — pin 2 on yours.
Debounce
Filtering the mechanical chatter of a switch so one press reads as one press.
Ground clip
The black lead on a scope probe. Gives the scope a reference to measure against. Not optional.
Pk-pk
Peak to peak. The full height of a waveform, bottom to top.
BOOTSEL
The button you hold while plugging in to make the Pico appear as a USB drive.

Software and build

SDK
Software Development Kit. The Pico SDK is the library of functions like gpio_put and spi_write16_blocking.
API
Application Programming Interface. The set of functions a library offers you.
Toolchain
The compiler, assembler and linker that turn your C into a binary for a different processor.
Cross-compiler
A compiler that runs on your Mac but produces code for the Arm chip.
arm-none-eabi
The compiler’s target name: Arm architecture, none meaning no operating system, eabi meaning embedded application binary interface.
newlib
The small C standard library built for embedded targets. Its absence is what broke the Homebrew compiler.
.uf2
USB Flashing Format. The file you drag onto the board.
.elf
Executable and Linkable Format. The full binary with debug information; the .uf2 is derived from it.
CMake
Describes how to build a project. Reads your CMakeLists.txt.
Ninja
The tool that actually runs the compiler commands CMake generates.
stdio
Standard input/output. What printf belongs to; it has to be pointed at UART or USB.

Course

CDE
Cumulative Design Experience. Cornell’s label for a course that pulls together the whole curriculum.
Merlin
Cornell Ornithology’s bird ID app. The judge of whether your synthesis is convincing.
Checkpoint
The weekly checkoff a TA signs. Cumulative — week 2 includes everything from week 1.
