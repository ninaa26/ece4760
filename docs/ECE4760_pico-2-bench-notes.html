00 — SETUP

Getting the project to build

Raw note

Set no for the second question thing For everywhere that says led pin switch to 25

Why the LED pin becomes 25

Demo code usually writes PICO_DEFAULT_LED_PIN instead of a number, so the same source builds for any board. That macro only resolves to a real GPIO if the board definition has one. On a plain Pico 2 the onboard LED sits on GPIO 25, so hard-coding 25 is exactly equivalent and removes the dependency on the board header being picked up correctly.

The reason the macro is fragile: on the wireless boards (Pico W, Pico 2 W) the LED isn't wired to an RP2350 pin at all — it hangs off a GPIO on the CYW43 wireless chip, and you have to drive it through the wireless driver. So "just use 25" is the safe move for the non-W board on your bench, but it is a board-specific number, not a universal one.

// the portable version, which may not resolve
#define LED_PIN PICO_DEFAULT_LED_PIN

// what we're doing instead
#define LED_PIN 25

gpio_init(LED_PIN);
gpio_set_dir(LED_PIN, GPIO_OUT);
gpio_put(LED_PIN, 1);

01 — ENTRY POINT

Where the code starts executing

Raw note

Code starts executing is first line of main It is initializing gpio

For your purposes, execution begins at the first line of main(). That is where you set breakpoints, and that is the first line you own.

Strictly, a fair amount has already happened before main() is reached, and it's worth knowing because it explains what the debugger shows you if you halt too early:

  1. The bootrom (mask ROM baked into the RP2350) runs, checks for BOOTSEL, and validates the image in flash.
  2. A small second-stage bootloader configures the QSPI flash interface so the chip can execute code directly out of flash (XIP — execute in place).
  3. C runtime startup copies initialised data into RAM, zeroes the .bss section, and sets up the stack and vector table.
  4. SDK runtime init brings up clocks and enabled peripherals.
  5. main() is called.

What those first lines of main are doing

The opening lines are almost always initialising GPIO — claiming pins and deciding what each one is for. Nothing on the chip is usable until you say who owns it.

int main() {
    stdio_init_all();            // USB/UART serial for printf
    gpio_init(LED_PIN);          // pin -> SIO function, output disabled
    gpio_set_dir(LED_PIN, GPIO_OUT);  // now make it an output
    while (true) {
        gpio_put(LED_PIN, 1);
        sleep_ms(250);
        gpio_put(LED_PIN, 0);
        sleep_ms(250);
    }
}

gpio_init() is doing two separate things: it routes the pin to the SIO function (software control — see §05) and it puts the pin in a known, safe state. It does not make the pin an output. That takes a second call.

02 — METHOD

Investigating code you don't recognise

Raw note

Investigate what code u knot know what it does Rp2350 hardware api guide - describes all functions hardware gpio section - table that tells u all functions for gpio number Scroll down and there is a bunch of functions U can select the function and it tells u what it does Right click and select definition Through functions we are going down through abstractions Look at hardware field Rp2350 datasheet list of registers

Two complementary moves: read the API doc to find out what a function is supposed to do, and Go to Definition to find out what it actually does. The second one is the skill worth building, because every SDK call bottoms out at a register write, and once you can see that register write you can debug anything.

The documentation route

  • Pico SDK Hardware APIs — raspberrypi.com/documentation/pico-sdk/hardware.html. Every hardware module is a section: hardware_gpio, hardware_spi, hardware_timer, hardware_adc, hardware_irq.
  • In hardware_gpio, the top of the page carries the function-select table — every GPIO number down the side, every peripheral function across the top (§03). Scroll past it and you get the full list of callable functions; click any one for its description, arguments and return value.
  • RP2350 datasheet — the register-level reference. When the SDK doc isn't enough, this tells you what each bit in each register means.

The Go-to-Definition route

Right-click any SDK call in VS Code → Go to Definition (F12). Keep doing it. You are walking down the abstraction stack, and each rung strips away one layer of convenience:

  1. 1gpio_put(25, 1)The friendly SDK call you write. Named for what you want, not for what the hardware is.
  2. 2static inline void gpio_put(...)A thin inline wrapper in hardware/gpio.h. It just chooses between the set and clear registers.
  3. 3sio_hw->gpio_set = 1u << 25A write through a hardware struct. sio_hw is a C struct laid over a fixed memory address so that struct fields line up with hardware registers. This is the "hardware field" layer.
  4. 4#define SIO_BASE 0xd0000000The struct's address, defined in the generated register headers along with every offset and bit mask.
  5. 5RP2350 datasheet, SIO chapterThe register list: what GPIO_OUT_SET is, what happens when a bit in it is written, and what the hardware does next.
The point

Nothing in the SDK is magic. A "function" is a name for a memory write. When something misbehaves, you can descend to the register, then look at that exact address in the debugger's memory view and see whether the bit you expected is set.

03 — PIN MUX

The GPIO function-select table

Raw note

hardware gpio section Table that tells u all functions for gpio nimber SPIO GPIO SIO SDK

Each GPIO pin is a multiplexer. The pad is physical; what is connected to it is a choice. Every pin can be attached to exactly one function at a time, chosen from a numbered list F0–F11 on the RP2350, and not every function is available on every pin. That constraint is what the table exists to answer, and it is why your DAC has to live on particular pins.

Naming trap

Your note has "SPIO" — that is SPI0 (SPI peripheral zero, a digit), not "SPIO". There are two SPI blocks, SPI0 and SPI1. Similarly SIO is a completely different thing from SPI — letters transposed, meaning unrelated. See §05.

// selecting a function = writing the mux
gpio_set_function(6, GPIO_FUNC_SPI);   // GPIO 6 becomes SPI0 SCK
gpio_set_function(7, GPIO_FUNC_SPI);   // GPIO 7 becomes SPI0 TX  (MOSI)
gpio_set_function(5, GPIO_FUNC_SPI);   // GPIO 5 becomes SPI0 CSn

Handing CS to the SPI peripheral means the hardware raises and lowers it around each frame for you. Drive CS yourself with SIO instead if you need one CS assertion to span several frames.

04 — ELECTRICAL

Inputs, outputs and impedance

Raw note

Automatically an output Inputs are high impediments Outputs are low impedance (can blow it)

"Impediments" is impedance. The distinction matters because it's the one that lets you destroy a pin.

Input — high impedance

A pin configured as an input presents a very large resistance to whatever is connected. It senses voltage and draws essentially no current. High impedance is electrically polite: connect an input to anything and nothing bad happens. It also means a floating input has no defined value, which is why you add a pull-up or pull-down when a pin isn't always driven.

Output — low impedance

A pin configured as an output forces its voltage to 0 V or 3.3 V, and it does that by being a low resistance to ground or to the supply. Low impedance means it will source or sink whatever current the circuit demands. If you tie a driven-high output to ground, or short two outputs together where one drives high and the other drives low, current is limited only by the pin's own on-resistance. That is how you cook a pin.

Correction to the raw note

The note says "automatically an output". In the Pico SDK it is the other way round, and the SDK header is explicit: gpio_init() selects the SIO function, clears the output enable (i.e. sets the pin to input) and clears the output value. You must call gpio_set_dir(pin, GPIO_OUT) to make it an output.

This default is deliberate and follows directly from the paragraph above: after reset, every pin is high-impedance, so a chip powering up cannot fight whatever is wired to it. Booting into "output" would risk exactly the short described above. Double-check what was actually said in lecture — it may have been "once you set the direction, it stays an output," or it may have been about a specific peripheral function.

Practical rules

  • Never wire two outputs together.
  • Never drive an output into a supply rail or ground.
  • Set direction before you set a value, if the initial level matters.
  • An input reading garbage that changes when you touch the board is a floating pin — add a pull.
05 — SIO

SIO, and what a register actually is

Raw note

Look at hardware field Rp2350 datasheet list of registers Go to memory and look at specific memory adress SIO

SIO = Single-cycle I/O

SIO is the block that gives software direct control of the pins. Its distinguishing feature is where it lives: SIO is attached directly to the processor's own bus port at 0xd0000000, not out on the shared peripheral fabric with SPI, UART and the rest. A read or write to a SIO register therefore completes in one clock cycle, with no bus arbitration. That is why toggling a pin through SIO is fast enough to time an ISR with an oscilloscope.

SIO also holds a few other things that need to be fast: the per-core CPUID, the inter-core FIFOs and spinlocks, the hardware dividers, and the interpolators.

Memory-mapped registers

A register is a fixed memory address that isn't memory. Writing to it changes hardware state; reading it reports hardware state. Everything you do to a peripheral is a load or a store to one of these addresses. In the SDK they are reached through structs (sio_hw->..., timer_hw->..., spi_get_hw(SPI_PORT)->...) laid over a base address — that is the "hardware field" your note refers to.

The SET/CLR/XOR aliases exist so you can change one pin without a read-modify-write on all of them. A read-modify-write can be interrupted halfway through; a single store to GPIO_OUT_SET cannot. So gpio_put(25,1) compiles to one store to 0xd0000018 with bit 25 set.

// these three lines are equivalent
gpio_put(25, 1);
sio_hw->gpio_set = 1u << 25;
*(volatile uint32_t *)(0xd0000018) = (1u << 25);
Using this in the debugger

Halt the program and open the memory view at 0xd0000010. Bit 25 of that word is the LED's driven state; you can watch it flip as you step. Same trick for 0xd0000030 to confirm the pin really is an output.

06 — TOOLING

Run mode vs debug mode

Raw note

No debug mode it just runs Debug mode program goes on and then it halts U can set breakpoints Go to memory and loook at specific memory adress Next

Without the debugger

You drag a .uf2 onto the board (hold BOOTSEL while plugging in, board mounts as a USB drive) and the program simply runs from power-up. You cannot pause it. Your only visibility is what you deliberately emit — printf over USB serial, an LED, or a GPIO you toggle and watch on the scope.

With the debugger

A debug probe connects to the SWD pins and speaks to the chip's debug hardware. VS Code loads the .elf (which carries the symbol and line information the .uf2 doesn't), runs to the start of main(), and halts there. From that halt you get:

  • Breakpoints — click the gutter to the left of a line number; execution stops when it reaches that line.
  • Step over / into / out — one line at a time. "Into" is how you walk into an SDK function and watch the abstraction ladder from §02 in motion.
  • Variables and watch — locals in scope at the halt, plus expressions you add yourself.
  • Memory view — type a raw address (e.g. 0xd0000010) and read the bytes there. This is how you inspect a peripheral register directly.
  • Call stack — how you got to this line.
  • Disassembly — the actual instructions, when the C isn't telling the truth.
Timing caveat

Halting stops the CPU, but it does not stop the world. The 64-bit microsecond timer keeps counting and external hardware keeps going, so anything timing-dependent — your 50 kHz DDS interrupt, the DAC, a signal you're capturing — will be wrong the instant you break inside it. To measure how long an ISR takes, don't breakpoint it: set a GPIO high on entry, low on exit, and measure the pulse on the scope. Lab 1 asks you to do exactly this.

SPI in one paragraph

Synchronous, full-duplex, one controller and one or more peripherals, four wires. SCK is the clock, generated by the controller. MOSI carries data controller → peripheral, MISO carries it back the other way, and CS (active low) selects which peripheral is listening. Mechanically it is two shift registers wired into a ring: on each clock edge one bit leaves the controller and one bit enters it, so a 16-bit transfer both sends 16 bits and receives 16 bits, whether or not you care about what came back. With a DAC you don't — the MCP4822 has no MISO at all, so GPIO 4 is declared and left unused.

CPOL and CPHA

Two bits that define when data is valid relative to the clock. CPOL = whether the clock idles low (0) or high (1). CPHA = whether data is sampled on the first clock edge (0) or the second (1). Four combinations, called modes 0–3. The peripheral's datasheet dictates which you use — the MCP4822 accepts (0,0) or (1,1), and Lab 1 uses (0,0).

spi_init(SPI_PORT, 20000000);              // 20 MHz baud rate
spi_set_format(SPI_PORT, 16, 0, 0, 0);     // 16 data bits, CPOL=0, CPHA=0, MSB first
gpio_set_function(PIN_MISO, GPIO_FUNC_SPI);
gpio_set_function(PIN_SCK,  GPIO_FUNC_SPI);
gpio_set_function(PIN_MOSI, GPIO_FUNC_SPI);
gpio_set_function(PIN_CS,   GPIO_FUNC_SPI); // hardware drives CS per frame

Reading a datasheet to talk to a chip

"Sdi device data sheets gibes u all info" — the four sections that matter, in order: pinout (what to wire), electrical characteristics (supply range, max clock rate), timing diagrams (which SPI mode, setup/hold, how long a conversion takes), and the command / register map (what the bits mean). 08 — DAC

The MCP4822 command word

A DAC turns a number into a voltage — the mirror image of the ADC you'll use for the potentiometer. The MCP4822 is a dual-channel, 12-bit DAC with a built-in 2.048 V reference, so it takes a number 0–4095 and produces a voltage without needing an external reference.

You talk to it with exactly one 16-bit SPI frame per update. Four config bits, then twelve data bits:

A/B 0 = channel A, 1 = channel B BUF reference input buffer, 0 = unbuffered GA 1 = ×1 gain, 0 = ×2 gain (active low) SHDN 1 = output active, 0 = shut down

So the config nibble used in the demo code is:

#define DAC_config_chan_A 0b0011000000000000  // A, unbuffered, gain 1x, active
#define DAC_config_chan_B 0b1011000000000000  // B, unbuffered, gain 1x, active

// merge config with a 12-bit sample and send one frame
DAC_data = DAC_config_chan_A | (value & 0x0fff);
spi_write16_blocking(SPI_PORT, &DAC_data, 1);

The & 0x0fff matters: anything above bit 11 would corrupt your config bits and silently change channel or shut the output off.

Output voltage

With the internal 2.048 V reference and 12 bits:

Vout = Vref × (D / 4096) × G     where Vref = 2.048 V, G = 1 or 2

G = 1  →  0 to 2.046 V,  step = 0.5   mV
G = 2  →  0 to 4.092 V,  step = 1.0   mV   (clipped by VDD = 3.3 V)

At 3.3 V supply you stay on gain ×1, because ×2 asks for more headroom than the supply has.

Unsigned DAC, signed sine

The DAC only accepts 0–4095, but a sine swings either side of zero. The fix is a DC offset: the sine table is built over ±2047 and you add 2047 before sending, which centres the waveform at roughly half of full scale. On the scope you'll see the sine riding on about 1 V of DC — that is correct, and the audio coupling capacitor removes it before the speaker.

LDAC

The MCP4822 has an input latch and an output latch. A write lands in the input latch; pulling LDAC low transfers it to the output. Tie LDAC to ground and every write takes effect immediately. Its real purpose is making both channels change at exactly the same instant: write A, write B, then pulse LDAC once.

Sanity check on the scope

The DAC settles in a few microseconds, so at 50 kHz (20 µs per sample) you're comfortably inside spec. If the output is a flat line, check SHDN (bit 12) is 1 and CS is actually toggling; if the waveform is stepped and jagged, you're either at too low a sample rate or your 12-bit values are wrapping.

09 — DDS

The timer interrupt and Direct Digital Synthesis

The timer

The RP2350 has two 64-bit counters that tick once per microsecond, and each has four alarm registers with their own interrupt lines. You write a future timestamp into an alarm register; when the low 32 bits of the counter match it, the interrupt fires. Alarms are one-shot — to get a periodic interrupt you re-arm inside the handler.

#define ALARM_NUM 0
#define ALARM_IRQ TIMER_IRQ_0
#define DELAY 20                 // microseconds -> 50 kHz

hw_set_bits(&timer_hw->inte, 1u << ALARM_NUM);   // enable this alarm
irq_set_exclusive_handler(ALARM_IRQ, alarm_irq);  // point IRQ at our function
irq_set_enabled(ALARM_IRQ, true);                 // enable it on the CPU
timer_hw->alarm[ALARM_NUM] = timer_hw->timerawl + DELAY;  // arm it

static void alarm_irq(void) {
    hw_clear_bits(&timer_hw->intr, 1u << ALARM_NUM);       // ack, or it re-fires forever
    timer_hw->alarm[ALARM_NUM] = timer_hw->timerawl + DELAY; // re-arm
    // ... DDS + SPI write go here ...
}

Two things bite people here. Forgetting to clear the interrupt flag means the handler is re-entered immediately and the program appears to hang. And everything inside the handler must finish in well under 20 µs, or you miss the next alarm — which is why the ISR uses integer maths and a lookup table rather than calling sin().

What DDS is

You want a sine at an arbitrary frequency, produced by integer arithmetic only. The idea: keep a phase accumulator — a 32-bit unsigned integer representing your position around one cycle, where the full 32-bit range is exactly 360°. Every sample, add a fixed phase increment. The accumulator overflows naturally at the top of the cycle, which is exactly the wraparound a phase needs. Use the top 8 bits as an index into a 256-entry sine table.

volatile unsigned int phase_accum_main;
volatile unsigned int phase_incr_main = (800.0 * two32) / Fs;  // 800 Hz

// once, at startup: build the table
for (int i = 0; i < 256; i++)
    sin_table[i] = (int)(2047 * sin((float)i * 6.283 / 256.0));

// every ISR:
phase_accum_main += phase_incr_main;
int sample = sin_table[phase_accum_main >> 24];   // top 8 bits = index 0..255
DAC_data = DAC_config_chan_A | ((sample + 2047) & 0x0fff);
spi_write16_blocking(SPI_PORT, &DAC_data, 1);

The one formula to remember

phase_incr = (f_desired × 2^32) / f_sample

Worked example, 800 Hz at 50 kHz: (800 × 4294967296) / 50000 = 68719476. Add that 50,000 times and you have advanced 800 full turns — 800 Hz, exactly. Change one variable and the frequency changes on the next sample, with no clicks and no recomputed table. That is the whole appeal, and it's what makes a swept chirp (a cardinal's song) easy.

Why the top bits

The accumulator has 32 bits of phase resolution but the table only has 256 entries, so you take the most significant 8 bits (>> 24) as the index and let the remaining 24 bits accumulate fractional phase. Frequency resolution is f_sample / 2^32 ≈ 12 µHz at 50 kHz — far finer than the table alone would give.

Fixed point

Floating point in an ISR is slow. Fixed point stores a fractional number in an integer by agreeing where the binary point sits — the course convention is 1.15.16, one sign bit, 15 integer bits, 16 fraction bits. Addition and subtraction are plain integer ops; multiplication needs a shift afterwards to put the point back. The phase accumulator above is fixed-point thinking already: it's a 0.32 fraction of a cycle.

10 — REFERENCE

Acronyms

ADC
Analog-to-Digital Converter. Voltage in, number out. Reads the potentiometer.
CS / CSn
Chip Select, active low. Tells one SPI peripheral that this frame is for it.
CPOL / CPHA
Clock polarity and phase — the two bits that define an SPI mode.
DAC
Digital-to-Analog Converter. Number in, voltage out. The MCP4822.
DDS
Direct Digital Synthesis. Phase accumulator + lookup table = arbitrary frequency.
GPIO
General Purpose Input/Output. A pin you control.
IRQ / ISR
Interrupt Request, and the Interrupt Service Routine that handles it.
LDAC
Load DAC, active low. Moves the input latch to the output latch.
MOSI / MISO
Controller-out-peripheral-in and the reverse. Also written COPI/CIPO.
PIO
Programmable I/O. Tiny state machines that generate protocols in hardware.
SDI
Serial Data In — the MCP4822's name for the pin you drive with MOSI.
SDK
Software Development Kit. Raspberry Pi's C/C++ libraries for the RP2040/RP2350.
SIO
Single-cycle I/O. Direct software pin control, one cycle per access. Not SPI.
SPI
Serial Peripheral Interface. SCK, MOSI, MISO, CS. Two blocks: SPI0, SPI1.
SWD
Serial Wire Debug. The two-wire link the debug probe uses.
UF2
The drag-and-drop firmware file format. No symbols — the debugger wants the .elf.
XIP
Execute In Place. Running code straight out of external flash.
