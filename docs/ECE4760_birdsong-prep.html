PART 0

The background you actually need

The chip

A microcontroller is a whole computer on one chip: a MIPS CPU at 40 MHz, 32 KB of RAM, 128 KB of flash, and — the part that matters here — a pile of peripherals: timers, SPI, UART, ADC, I/O pins.

The mental model that makes embedded C click: peripherals are hardware that runs independently of your code. You configure them by writing to registers, and then they just go — counting, shifting bits out, sampling voltages — while the CPU does something else. Your program mostly sets them up and reacts when they signal you.

I/O pins

Every pin is either an input (read a voltage) or an output (drive 3.3 V or 0 V). Three registers:

  • TRISx — direction. 0 = output, 1 = input. Mnemonic: 0 looks like Output, 1 looks like Input.
  • PORTx — read the actual pin voltage.
  • LATx — the latch, what you are driving out. Always write LAT, read PORT.

The chip also has peripheral pin select: SPI and UART signals can be routed to different physical pins in software. That is what lines like PPSOutput(2, RPB5, SDO2) do — "send SPI2's data-out to pin RB5."

Timers and interrupts

A timer is a counter in hardware. It ticks every peripheral-clock cycle — 0, 1, 2, 3 … — and when it reaches the value in its period register (PR2 for timer 2), it resets to zero and raises a flag. That is the entire peripheral. Two knobs: the prescaler divides the clock before counting, and the period register sets how high it counts.

An interrupt is the hardware saying "stop what you are doing and run this function now." When the timer rolls over it sets its flag; if that interrupt is enabled, the CPU jumps into your ISR, runs it, and returns to exactly where it was. Your main code never notices.

This is how you get precise timing. A delay loop in main() would jitter every time other code ran; a timer interrupt is spaced by hardware.

The audio path

DDS — the core trick

You want an arbitrary frequency from integer math, fast. A 256-entry sine table stepped one entry per sample gives you exactly one frequency. Step by two and you get double. Step by 1.5? You cannot — integers.

So: keep a 32-bit phase accumulator, add a constant increment to it every sample, and let it overflow. The overflow is the wrap from 2π back to 0. Use only the top 8 bits as your table index.

phase_accum += phase_increment;          // 32-bit; overflow is the point
output = sine_table[phase_accum >> 24];  // top 8 bits = index 0..255

ProtoThreads

There is no operating system here. ProtoThreads is a header full of macros that lets you write several concurrent-looking loops — scan the keypad, sequence the song — that hand control back to each other. It is cooperative: a thread runs until it hits a PT_YIELD and gives up the CPU. Nothing preempts it.

The critical thing: ProtoThreads are not for real-time work. Your 44 kHz audio lives in the timer ISR, which is real hardware preemption. Threads handle the slow stuff — keypad every 30 ms, song sequencing, terminal output.

Also: threads have no stack of their own, so local variables do not survive a yield. Declare them static.

Fixed point

There is no floating-point hardware. float math is emulated in software and far too slow for a 22 µs ISR. So you scale fractions by a power of two and store them as integers. The course convention is 1.15.16: a signed 32-bit int with 16 integer bits and 16 fraction bits, so 1.0 is stored as 65536. Addition is plain integer addition; multiplication needs a shift afterward.

Q1

Pin current limits

Answer

15 mA from any one I/O pin.
200 mA summed across all ports.

Straight from the Absolute Maximum Ratings table (section 29.0) of the PIC32MX1XX/2XX datasheet:

Absolute Maximum Ratings — DS61168E, p.243
Maximum current out of VSS pin(s)300 mA
Maximum current into VDD pin(s)300 mA
Maximum output current sunk by any I/O pin15 mA
Maximum output current sourced by any I/O pin15 mA
Maximum current sunk by all ports200 mA
Maximum current sourced by all ports200 mA
Watch out

A lot of circulating answers say 25 mA. That is the PIC32MX3XX/4XX family — the older 4760 chip. For the 2XX part you are actually using it is 15 mA.

Why you care: these are absolute maximums — exceeding them can permanently damage the chip, and it is the classic way to kill a board. Practically: never drive a speaker, motor, or bare LED straight off a pin without a series resistor.

Note the two limits are independent. You cannot pull 15 mA from fourteen pins at once, because 14 × 15 = 210 mA blows the 200 mA total budget. And absolute max is the damage threshold, not the current at which the pin still produces a valid logic level — for a clean 3.3 V output, stay well under it.

Q2

What hardware does ProtoThreads use?

Answer

Timer 1 and its interrupt, for the millisecond system tick behind PT_YIELD_TIME_msec(). Timers 2, 3, 4 and 5 are all free — so yes to all three parts of the question.

From the ProtoThreads page: "Moved thread system timer to timer 1 for better use of more flexible timers 4 and 5." That change is exactly why the answer is yes — system timing was deliberately moved off Timer 5 so you get the flexible 16-bit timers.

It also uses, only if you enable the optional serial/debug features: UART2 for the terminal thread, DMA channel 1 for UART2 transmit, and CVrefOut (pin 25) for the scope-debug feature. And it depends on the interrupt system being live — the page warns that turning interrupts off, or failing to turn them on, crashes ProtoThreads. Do not touch Timer 1's control registers.

Two caveats worth carrying into lab. First, older versions of the library used Timer 5 — that is why you will find a different answer in old lab reports. Trust the header you were given; grep -n "OpenTimer" pt_cornell_1_3_2.h settles it in seconds. Second, timers pair into 32-bit units (Timer2+3 becomes "Timer23", Timer4+5 becomes "Timer45"), and opening a 32-bit timer consumes both halves. You only need 16 bits here, so it should not come up.

Q3

Setting up the 44 kHz audio timer

Part 1 — how many cycles?

With prescaler 1, the timer counts at the peripheral bus clock, which is 40 MHz here — one tick every 25 ns.

40,000,000 ÷ 44,000 = 909.09 cycles per interrupt
Answer

909 timer cycles

A nuance worth knowing: OpenTimer2 takes the period register value, and the timer counts 0 through PR2 inclusive — that is PR2 + 1 cycles. So PR2 = 909 actually gives 910 cycles, or 43,956 Hz: about 0.1 % low and completely inaudible. 909 is the expected answer. If you want to be pedantic, PR2 = 908 lands on 44,004 Hz. Either is defensible — just be consistent, and use your actual Fs when you compute DDS increments.

Internalize what 909 means: that is your entire ISR budget. Every sample you have ~909 CPU cycles for all the DDS, envelope, and SPI work. Plenty for integer math; nowhere near enough for sin() or floating point.

Part 2 — three lines of code

// 1. on, internal clock, prescaler 1:1, period 909
OpenTimer2(T2_ON | T2_SOURCE_INT | T2_PS_1_1, 909);

// 2. enable the Timer2 interrupt at priority 2
ConfigIntTimer2(T2_INT_ON | T2_INT_PRIOR_2);

// 3. clear the interrupt flag
mT2ClearIntFlag();
  • T2_ON starts it. T2_SOURCE_INT counts the internal peripheral clock rather than pulses on a pin. T2_PS_1_1 is the 1:1 prescaler. 909 goes into PR2.
  • T2_INT_ON unmasks the interrupt; T2_INT_PRIOR_2 sets priority 2. This priority must match the ipl in your ISR declaration — a mismatch is a silent failure where the ISR simply never runs.
  • Clearing the flag before you start avoids taking a stale interrupt immediately.

The matching ISR:

void __ISR(_TIMER_2_VECTOR, ipl2 SOFT) Timer2Handler(void)
{
    mT2ClearIntFlag();     // clear it FIRST, always
    // accumulate phase, look up sine, apply envelope,
    // then write the sample out over SPI to the DAC
}

Note ipl2 matching T2_INT_PRIOR_2. Higher number means more urgent; priority 2 sits comfortably above the ProtoThreads Timer 1 tick.

Q4

DDS frequency resolution

The accumulator is 32 bits, so the smallest change you can make to the increment is 1. Rearranging the DDS equation:

Δf = Fs / 232 = 44,000 / 4,294,967,296
Answer

1.02 × 10−5 Hz — about 10 microhertz

Using the true 43,956 Hz sample rate: 1.023 × 10−5 Hz. Same answer.

What this means intuitively: the resolution is absurdly, uselessly fine — you could specify a frequency to five decimal places. That is the whole beauty of DDS. Your sine table is only 256 entries, a coarse approximation, but your frequency control is essentially continuous, because the precision lives in the accumulator's low 24 bits rather than in the table.

At 10 µHz resolution, two oscillators one step apart would take over a day to drift a full cycle out of phase. For birdsong you will be sweeping across hundreds or thousands of Hz, so you have far more resolution than you need — which is exactly what makes the chirp glide smoothly. Nudge the increment by a tiny amount each sample and you hear a continuous sweep with no stepping.

One footnote

The question says use an int, which is signed 32-bit. Signed overflow is undefined behavior in C, and it complicates your table-index math. Use unsigned int (and volatile if the ISR shares it) so the wraparound is well defined. The resolution is Fs/232 either way.

Q5

Alternatives to a linear ramp

First, why you need an envelope at all. Switch a sine wave on and off instantly and the discontinuity produces a broadband click — a step function has energy at every frequency. It pops, and it sounds nothing like a bird. An envelope is just an amplitude multiplier: output = envelope * sine_value.

The governing principle: the smoother the envelope, the less spectral splatter. A hard gate is discontinuous in the signal itself — worst. A linear ramp is continuous but has a corner, a discontinuity in the slope, which still splatters, just less. Envelopes with smooth derivatives splatter least.

Exponential — one-pole IIR

amp = amp + ((target - amp) >> k);   // one shift, no multiply
  • Extremely cheap: a subtract and a shift. No table, no state machine.
  • Sounds the most natural — physical resonators (a plucked string, a bell, a bird's syrinx) decay exponentially.
  • No slope corner at the start of the decay.
  • But it is asymptotic: it approaches the target without reaching it, so you need a threshold for "close enough to zero" or a faint tone lingers.
  • And rise time is not a direct parameter — you tune k and measure, and as a shift you only get power-of-two time constants.

Raised cosine — Hann window

env = 0.5 × (1 − cos(πt/T))

  • The best-sounding option: slope is zero at both endpoints, so there is no corner at all and minimal splatter. Cleanest possible attack and release.
  • But it needs a cosine table (memory) or a second accumulator to scan it, plus a multiply per sample.
  • Nice trick: scan a cosine table with a second phase accumulator — the same DDS technique — and one fixed table gives you any envelope duration.

ADSR — piecewise linear

  • Far more expressive than one ramp: a percussive attack with a long tail is much closer to real birdsong structure.
  • Still just integer adds, so nearly as cheap as a plain ramp.
  • But it is a state machine with counters and per-stage rates — more code, more to debug.
  • And it still has corners at every stage boundary, though mid-note they are far less audible.

Gaussian

  • The optimal time–frequency tradeoff — minimum time-bandwidth product, so it is the least smeared in frequency. A genuinely good model for natural chirps.
  • But it has infinite support, so truncating reintroduces a small discontinuity.
  • And it is expensive — realistically you would table it, at which point a raised cosine is simpler.

Arbitrary table lookup

  • Total control: trace the envelope off a real cardinal spectrogram and reproduce it exactly. One lookup per sample.
  • With a DDS-style accumulator indexing it, one table serves any duration.
  • But it costs memory, and you generate the table offline.

No envelope — the baseline you are avoiding

  • Free, and audibly wrong: a click on every note plus broadband noise.
Practical recommendation

The linear ramp is recommended because it is cheap and good enough — a corner in the slope is far less objectionable than a step in amplitude. For the biggest improvement per line of code, switch the decay to exponential: one shift per sample and the notes stop sounding synthetic. If you are chasing polish, a raised-cosine attack with an exponential decay is the combination that sounds best.

LAB

Three things most likely to bite you

01

Missing static in a thread.

Any local variable in a ProtoThread that must survive a yield has to be static. Non-static locals are garbage after the thread resumes.

02

Missing volatile on an ISR-shared variable.

If main code reads something the ISR writes, mark it volatile or the compiler caches it in a register and never sees the change. You will chase a phantom bug for an hour.

03

Interrupt priority mismatch.

T2_INT_PRIOR_2 must match ipl2 in the __ISR declaration. Otherwise the ISR silently never fires — no error, no warning, no sound.
